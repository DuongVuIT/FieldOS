# FieldOS Level 0 — React Native Foundation

## Goal

Bootstrap the smallest bare React Native application for learning how a React Native app starts and renders native UI, without introducing application architecture.

## Repository and environment

- The repository starts with only `README.md` and Git metadata.
- No `MASTER_RULES.md` exists in the repository. The user-provided FieldOS Learning Rules are the applicable project rules for this milestone.
- Use Yarn for dependency installation and project scripts.
- The host is macOS ARM64 with Node.js 24, Xcode 16.3, CocoaPods 1.14.3, Java 17, and Android emulator definitions available.
- React Native 0.87.x is the current stable release at the time of this milestone. Use the React Native Community CLI and its current stable template.

## Design

Create a bare React Native project named `FieldOS` directly in the existing repository. Keep the native iOS and Android projects generated by the official template so the learner can inspect the real launch path. Use the generated TypeScript setup and make only the smallest UI change required by the milestone.

The application surface consists of one `App` component and one neutral screen-copy module:

```ts
export const screenName = {
  title: 'FieldOS',
  subtitle: 'Mobile Engineering Lab',
} as const;
```

`App.tsx` imports `screenName` through the `@/*` alias. The alias must work both for TypeScript checking and for the Metro/Babel runtime, so the project will contain the matching `tsconfig.json` path mapping and the smallest Babel module-resolver configuration needed to resolve `@/constants/screenName`.

The UI renders only the two requested text values. No navigation, data access, global state, persistence, native module, background work, telemetry, domain layer, repository, use case, or service is introduced.

## Startup path to teach

The final explanation will trace the actual generated project through:

```text
OS launch
→ native application target
→ React Native initialization
→ Hermes/runtime initialization
→ JavaScript entry point (`index.js`)
→ `App` render
→ native text/layout views
```

The explanation will identify the iOS and Android differences using the generated `ios/` and `android/` files rather than describing an abstract framework-only path.

## Hermes and New Architecture verification

Do not infer either setting from React Native defaults. After generation:

1. Inspect the generated Android Gradle properties and build configuration for the Hermes and New Architecture flags.
2. Inspect the generated iOS Podfile/native configuration for the corresponding settings.
3. Confirm the selected React Native version and engine in `package.json` and the installed dependency graph.
4. Use a successful native build/runtime check as evidence that the selected configuration is usable on the tested platform.

Record any platform limitation exactly. In particular, the current environment has reported a CoreSimulatorService failure and sandbox restrictions while starting ADB, so runtime verification may be Android-only or may require an approved native-environment command.

## Verification

Run the narrow checks supported by the generated project:

- TypeScript typecheck with the project's strict configuration.
- Generated lint command.
- Generated Jest test command, updating only starter expectations that refer to replaced copy.
- Android debug build and runtime attempt using an available emulator.
- iOS build/runtime attempt if the simulator service is available.

Review the final diff and report successful checks separately from environment-blocked checks. Do not claim a platform ran unless its output proves it.

## Out of scope

- React Navigation
- API calls or authentication
- SQLite or other persistence
- Zustand or TanStack Query
- Repository, use-case, domain, or sync-engine layers
- Telemetry or OpenTelemetry
- Background workers
- Custom native modules
- Future-facing application architecture
